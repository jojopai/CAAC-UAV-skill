# pi_agent_subagent_workflow 项目评估与适航审定技能设计

评估对象：https://github.com/melodylife/changworkshop_project_sharing/tree/main/pi_agent_subagent_workflow
评估日期：2026-09-26
评估方式：通读该目录全部 19 个文件（2 套示例工作流 + 12 个 agent 定义 + 编排脚本 + artifact 契约），并结合我们已建立的取证流程体系做适配性分析。

---

## 一、这个项目是什么

它不是在讲"多智能体"的概念，而是**两套可直接运行的、把主会话当编排者的工作流模板**：

| 示例 | 输入 | 阶段数 | 子代理角色 | 最终产物 |
|---|---|---|---|---|
| tour_planner | 一段旅行简述 | 7 阶段（Phase 0~6） | 5 个（researcher ×3 并行、synthesizer、critic、designer、generator） | 一个自包含 HTML 行程报告 |
| game_creator | 一段游戏简述 | 11 阶段（Phase 0~10） | 7 个（designer、critic、ui-designer、4 个并行 developer、dev-manager、qa-tester、deployer） | 本机 localhost 上可玩的网页游戏 |

架构要素（这部分才是真正有价值的）：

1. **主会话是唯一的编排者**，拥有全部阶段切换、产物目录与最终交付；所有子角色都是叶子节点（spawning: false）。
2. **阶段严格串行，只保留一个 fan-out 点**（trip 是 3 个研究员并行，game 是 4 个模块开发者并行）。
3. **产物契约（artifact contracts）先于执行被固定**：references/contracts.md 用 JSON/Markdown 结构把每个阶段的输入输出钉死，子代理只负责"按契约填"。
4. **机械检查交给脚本，判断交给模型**：每个关键阶段都先跑一个 Python 校验器，并明确写着"Treat its output as evidence, not a verdict"（把脚本输出当证据，不当判决）。
5. **先审计再美化**：critic 排在渲染之前，原话是 once the plan is pretty, nobody questions it（一旦做得漂亮，就没人质疑了）。
6. **有界修复循环 + 强制回归检查**：修复后必须单独做一轮 re-audit，除了确认原问题关闭，还必须主动寻找"修复引入的回归"；并规定"一轮关闭 1 条、新开 2 条 = 失败的一轮"。
7. **确认门（Gate）当轮提问**：明确禁止把问题攒到最后，一次最多问 3 条，每条给"问题 + 为什么重要 + 建议怎么办"。
8. **证据物化（evidence materialization）**：fan-out 之前先由脚本把公共数据抓成一份 evidence.json，子代理读它而不是各自重复抓取、重复失败。
9. **按角色分配 thinking 等级**：事实采集用 low，唯一决定质量的那一步用 high，机械操作用 low。
10. **fire-and-forget，禁止轮询**：spawn 后结束父轮次，靠完成回调恢复，明确禁止 poll / sleep / tail。
11. **绝不允许编造**：风格规则写死 Never invent prices, opening hours, travel times, or addresses，并有一句很到位的话——**Prefer a visible gap over a confident guess, every single time（宁可暴露空白，绝不给出自信的猜测）**。
12. **另有 REVIEW-REPORT.md** 记录了仓库对外分享前的脱敏复核：代理地址、绝对路径、真实地名、真实账户 ID、第一人称与家庭信息全部清零，并用脚本校验 fenced JSON 语法。

## 二、评估：哪些思路能直接用，哪些不能

### 2.1 高价值、可直接迁移的

| 该项目的做法 | 对我们对应的东西 | 迁移判断 |
|---|---|---|
| 主会话编排 + 叶子角色 | 我们的 6 个分流程，每个步骤有明确责任方 | 直接可用 |
| 阶段串行 + 单一 fan-out | 我们 TC / DOA / POA 三条线并行，每条线内部串行 | 直接可用，且我们的并行点更明确 |
| artifact contracts 钉死产物结构 | 我们的判定报告、审定基础、符合性检查单、不符项台账、复核报告 | 直接可用，价值最高 |
| 脚本当证据、模型当判断 | 我们的条款溯源核对、时限一致性核对 | 已在做，值得固化成技能自带脚本 |
| 先审计再美化 | 我们的"复核在定稿前" | 直接可用 |
| 有界修复 + 回归检查 | CAAC 的不符合项整改 → 验证关闭，且必须防复发 | 高度契合，其 CLOSED/PARTIAL/NOT FIXED + Regressions 表格形状可直接借用 |
| 确认门当轮提问 | 我们的 6 个控制门 | 直接可用，尤其"最多 3 条"这条纪律 |
| 证据物化 | 我们已把 15 份法规提取成文本语料 | 已在做，这正是"子代理不许自己回忆条款"的基础设施 |
| 绝不编造 / 宁可暴露空白 | 法规文件写作纪律 | 必须照搬，且我们要更严 |
| 分享前脱敏复核 | 对外发布设计资料需脱敏 + 加 CAAC 声明 | 直接可用 |

### 2.2 不适用或必须改造的

| 该项目的做法 | 为什么不能照搬 |
|---|---|
| subagent()、.pi/skills/、caller_ping、model: deepseek/... 、用 .ts 扩展注册斜杠命令 | 运行时耦合。这些是 pi coding agent 的专有机制；Codex 里对应的是 spawn_agent / wait_agent / send_message，技能用 SKILL.md 发现，没有斜杠命令注册机制 |
| 循环预算"最多 2 轮" | 我们的驱动因素不是轮数而是**法定时限**（一类问题 21 个工作日、涉及安全不符项 5 个工作日答复 / 20 个工作日整改）。循环边界应由法规时限决定 |
| 面向"消费级产物"（好看的行程、好玩的游戏） | 我们的产物是**受监管的申报文件**，验收标准是法律性的、由外部（局方）判定，不是审美性的。因此不变量要硬得多 |
| 角色模型统一、thinking 分级 | 分级思路可用，但我们的角色划分依据是**专业领域**（设计保证 / 生产质量 / 适航批准），不是创作流水线 |

### 2.3 必须指出的短板

1. **关键的校验脚本没随仓库发布。** 工作流引用了 8 个脚本（trip-validate/validate_itinerary.py、trip-evidence/collect_evidence.py、game-qa/qa_playtest.py、game-serve/serve_game.py 等），仓库里一个都没有。而"脚本当证据"正是这个架构的承重墙——照抄它的 SKILL.md 只会得到一半。
2. **没有条款溯源机制。** 它的证据是 POI、天气、图片；我们的证据是**法规条款**。它那套 evidence.json 没问题，因为 POI 错了只是体验差；我们的条款引错会直接导致申报文件被退回。这一层必须由我们新增。
3. **对"外部权威"没有建模。** 它所有阶段都能由 AI 团队自己完成；我们的流程里有大量**只能由局方完成**的动作（受理、审查、颁证、监督），技能必须能区分"我们要做的"和"等局方做的"。
4. **保密性约束没有体现。** 设计数据、构型文件属于敏感信息，需要明确哪些内容可以进模型上下文、哪些只能留在本地。

### 2.4 结论

**能，而且它的架构比它的例子更有价值——但只能借骨架，必须换一套承重结构。**

借它三样东西：**主会话编排 + 阶段串行 + 单一 fan-out**、**artifact 契约**、**审计先于定稿 + 有界修复 + 回归检查**。
它缺的两样我们必须自己补：**条款级溯源与机器核对**、**局方动作与我们动作的分离建模**。

## 三、技能设计

### 3.1 设计目标

把已建成的流程体系（`取证工作流程/` 9 份文件）与法规语料（`适航审定程序源文件/`、`无人机法规与标准源文件/`）封装成一个可被 Codex 自动调用的技能，使它在接到适航取证相关请求时能：

1. 先判定类别与路线，再谈其他；
2. 产出**结构固定、条款可溯源、可被机器复核**的交付物；
3. 在定稿前完成复核，并在修复后做回归检查；
4. 允许并行，但只在受控的 fan-out 点并行，且给每个子代理传绝对路径与产物契约。

### 3.2 技能形态

名称：`uav-airworthiness-cert`
位置：`~/.agents/skills/uav-airworthiness-cert/`

```
uav-airworthiness-cert/
|-- SKILL.md                     入口：不变量 + 模式路由 + 委派规则
|-- references/
|   |-- regulation-map.md        法规地图：文件代号、本地路径、管什么、关键条款坐标
|   |-- contracts.md             产物契约：各类交付物的固定结构
|   `-- roles.md                 子代理角色与委派模板（Codex 版）
`-- scripts/
    |-- build_corpus.py          把 PDF 语料提取成可检索文本 + 索引
    |-- verify_citations.py      条款引用溯源核对
    `-- check_consistency.py     跨文件时限/术语一致性核对
```

### 3.3 SKILL.md 里要写死的六条不变量

这六条就是"改变了模型决策"的部分，也是本技能与通用写作技能的区别：

1. **条款必须溯源。** 任何条款号引用都要写出文件代号；不得凭记忆引用；交付前用 `verify_citations.py` 核对，未命中必须标出而不是静默保留。
2. **类别先行。** 未确定最大起飞重量、是否载人、是否融合飞行、是否在人口密集区上方飞行之前，不进入任何后续流程。
3. **时限是法定值。** 时限只能来自原文；脚本核不出就标注"待核实依据"。
4. **区分责任方。** 每一步标注"我方 / 局方"，局方动作不得写成我们的交付物。
5. **不编造。** 缺信息写"待确认"；置信度不足要显式说明。宁可暴露空白，不给自信的猜测。
6. **复核在定稿前，不能在提交前。** 修复后必须单独做回归检查；"关闭 1 条、新开 2 条"按失败轮次处理。

### 3.4 模式路由（对应 6 个分流程）

| 模式 | 触发场景 | 主要参考文件 |
|---|---|---|
| classify | 类别判定、路线选择、风险等级 | references/regulation-map.md |
| type-cert | 型号合格证、审定基础、符合性方法、试验大纲 | references/contracts.md |
| design-org | DOA、设计保证手册、独立监督、CVE | references/contracts.md |
| production-org | POA、质量手册、QSAC、CS、权益转让协议 | references/contracts.md |
| airworthiness | 适航证、特殊适航证、特许飞行证、实名登记 | references/regulation-map.md |
| post-cert | 设计更改、监督、不符合项整改、48 小时报告 | references/roles.md |
| review | 流程/文件复核、条款溯源核对、跨文件一致性 | scripts/ |

### 3.5 委派规则（从项目借来，翻译到 Codex）

| pi 的做法 | Codex 的对应 |
|---|---|
| subagent({agent, model, thinking, task}) | spawn_agent(task_name, message, fork_turns) |
| 完成后自动回调恢复父会话 | wait_agent 等待完成通知（长超时，不轮询） |
| caller_ping 子代理求助 | 子代理用 send_message / followup_task 回报 |
| frontmatter 固定 model/thinking | spawn 时指定 model / reasoning_effort |
| 传绝对 run 目录路径 | 同样：**每个子任务必须带绝对路径** |

必须保留的三条纪律：单一 fan-out 点、子代理是叶子节点、子代理不得自行"回忆"条款（只能引用语料文件中存在的条款）。

### 3.6 与现有文件的关系

| 现有资产 | 在技能中的角色 |
|---|---|
| 取证工作流程 00~08 | 技能的**知识来源**；技能不复制它们，而是指向它们 |
| 适航审定程序源文件、无人机法规与标准源文件 | **语料源**；build_corpus.py 把它们提取成可检索文本 |
| 适航审定执行 01~06 | 精读笔记与模板，作为参考件 |
| 08_复核审查报告 的核对方法 | 固化成 verify_citations.py 与 check_consistency.py |

### 3.7 已知局限（诚实声明）

1. 技能依赖本地语料目录存在；换机器需重新跑 build_corpus.py。
2. 《条例》PDF 无文字层，build_corpus.py 会把它标为"需 OCR"，相关条款核对需人工渲染。
3. 技能不能替代局方审查结论；它能保证的是**提交材料的内部一致性与可溯源性**。
4. 类别判定中若干参数（我方产品参数）尚未确定，技能在此只能给出条件分支，不能给出结论。

### 4.3 两点值得记录的观察

1. **反向测试比正向测试价值大得多。** 正向跑 259 条全绿，只说明"没报错"；正是反向测试（人为写入假条款）才逼出了脚本里那个静默跳过的分支缺陷。这与 pi 项目里那句话是一回事——**脚本输出是证据，不是判决**，而验证器本身也需要被验证。
2. **该技能无法替代人工判断的部分已写进文档而不是藏起来**：法规地图里显式列出"未纳入语料的规章（CCAR-21、AP-21-17、AP-21-32）禁止直接引条款号"，以及 5 处新旧文件冲突的当前处理方式。

## 五、拆分成三个技能的评估与落地

### 5.1 两条候选拆分轴

| 拆分轴 | 具体方案 | 评判 |
|---|---|---|
| **按工作线** | ① TC 线 ② DOA 线 ③ POA 线 | **不采纳**。适航批准与证后监督横跨三条线，落不到任何一个里面，实际会变成四个技能；而且三份程序的正文有大量交叉引用，按线切会把同一段规则复制三份 |
| **按功能** | ① 流程执行 ② 资料编写 ③ 复核审计 | **不采纳**。路由会重叠——"帮我准备 DOA 申请"同时命中前两个，模型无法稳定选择；而且三个校验脚本会被复制三份，正是要避免的浪费 |
| **按生命周期** | ① 判定与准入 ② 符合性与体系 ③ 颁证与维持 | **采纳**。边界与项目时间轴重合，路由可判定（用户说的是"还没开始/正在审/已经拿证"），且三段的耗时期差异最大，最能达到拆分的目的：**长期项目只加载当前阶段需要的内容** |

### 5.2 落地结果

| 技能 | 阶段 | 覆盖 | 文件数 |
|---|---|---|---|
| `uav-airworthiness-cert` | ① 判定与准入 | 类别判定、取证路线、申请资格与时机、受理、过渡期；**并持有共享底座** | 11 |
| `uav-cert-compliance` | ② 符合性与体系 | 审定基础、符合性方法、DOA 设计保证系统、POA 生产质量系统、两本手册、不符合项整改 | 4 |
| `uav-cert-sustain` | ③ 颁证与维持 | 颁证前置检查、适航证与特许飞行证、逐架机放行、证后更改、监督、报告义务、证件有效期 | 4 |

**共享底座不复制。** 语料、法规地图、产物契约、三个校验脚本与状态台账统一放在技能①内，技能②③以绝对路径调用（`~/.agents/skills/uav-airworthiness-cert/`），并在各自的 SKILL.md 里写明：该路径缺失时**停止并报告**，不得临摹一套替代品。这样既满足"拆成三个"，又不产生三份会各自漂移的脚本。

### 5.3 三项新要求如何变成可执行的能力

| 要求 | 原来只是一句原则 | 现在的机制 |
|---|---|---|
| **严格按所有规范要求** | "要符合规范" | 新增 `extract_requirements.py`：从语料原文提取全部强制语句（应当/必须/不得/严禁等），生成带条款号的**要求清单**；新增不变量第 7 条——**每一条要求都必须处置**（适用 / 不适用+理由 / 由专用条件确定），空处置即未关闭事项。实测 6 份文件共 566 条要求 |
| **完善相关资料** | "把资料补齐" | 新增 `references/deliverables-matrix.md`：按阶段列出**全部必需交付物及其依据条款**，并给出缺口分析五步法；缺口分类为 缺失 / 不完整 / 未生效 / 内容错误。**明确规定：已存在但缺字段的文件只补字段，不得另起一份新文件** |
